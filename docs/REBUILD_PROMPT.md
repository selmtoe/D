# 別のCodex向け: 3Dオンライン大富豪 完全再構築プロンプト

以下の依頼を、計画の提示だけで終わらせず、実装・テスト・修正・コミット・Pushまで完遂してください。

---

## あなたの役割

あなたは、オンラインゲーム、Three.js、リアルタイム分散状態、Firebase、3Dキャラクター、アクセシビリティ、モバイルUI、ゲームQAに精通したシニア開発チームとして行動してください。

既存の大富豪アプリを小手先で改修するのではなく、保守可能な構成でゼロから再構築してください。旧実装は画面と意図を確認するための参考資料に留め、巨大な単一HTMLやクライアント任せのルール判定を踏襲しないでください。

リポジトリ内の docs/DAIFUGO_RULEBOOK.md と docs/FIREBASE_HANDOFF.md を最初から最後まで読んでください。ルールブックをゲームルールの唯一の正本とし、Firebase引継ぎ資料を既存クラウド環境の正本として扱ってください。コード、旧挙動、一般的な大富豪、あなたの知識と矛盾しても、ルールブックを優先してください。疑問や矛盾があれば勝手に丸めず、所有者へ確認してください。

## 最終目標

次の品質を同時に満たす、3～6人用のオンライン大富豪を完成させてください。

- 完全3Dの高級プライベートカードサロン
- 本物の円卓を囲んでいるようなカメラ、照明、質感、カード操作
- 通常大富豪と、情報非対称のブラインド大富豪
- 途中観戦・上がり後観戦・プレイヤー切替カメラ
- Firebaseによる権威的なルール判定と再接続
- WebRTCによる低遅延の非権威イベント同期
- 将来ほかのゲームでも使える、完全3Dの共通アバター基盤
- PC、スマートフォン、タブレット、キーボード、タッチ、スクリーンリーダーに対応
- ルールテスト、複数クライアントテスト、E2E、視覚回帰、実運用スモークテストを完備

初回リリースでは大富豪以外のゲームを実装しないでください。将来追加できる構造にはしますが、オセロ、コネクトフォー、ヨット、神経衰弱、エアホッケーなどを今回の画面やナビゲーションへ混ぜないでください。

## 絶対条件

1. 3D方針を崩さないこと。円卓、カード、アバター、座席、演出はすべて3D空間を中心に作ること。
2. テーブルはモデル上で真円であること。楕円メッシュや非等方スケールでごまかさないこと。
3. 透視投影による自然な見かけの楕円は許容するが、極端な俯角や広角で不自然につぶさないこと。
4. ルール判定をクライアントだけで行わないこと。
5. ブラインド札の中身を所有者のクライアントへ送らないこと。CSSで裏返すだけの実装は禁止すること。
6. アバターを2D SVGや平面の顔画像で済ませないこと。実際の3Dメッシュ、マテリアル、共通リグを使うこと。
7. アバターの自由描画機能は作らないこと。
8. 既存ゲームや既存キャラクターのモデル、テクスチャ、UIを複製しないこと。
9. Wii Sports ResortやMiiの「親しみやすく一目で個体識別でき、ゲームをまたいで同じ自分を使う」という方向性だけを参考にし、造形・比率・パーツ・素材・UIは完全に独自にすること。
10. ロビーと入室導線は、豪華さより先に分かりやすさを優先すること。
11. 画面幅によって手札、ボタン、観戦UI、ログ、モーダルが重ならないこと。
12. プレースホルダー、ダミーボタン、未接続画面、TODO、握りつぶした例外を残して完成扱いにしないこと。

## 推奨技術構成

技術的な重大理由がない限り、次を採用してください。変更する場合は理由と同等以上の保証を文書化してください。

### フロントエンド

- TypeScript strict mode
- React + Vite
- Three.js + React Three Fiber
- Dreiは補助用途に限定し、重要な挙動をブラックボックス化しない
- XState、または明示的な判別共用体による有限状態機械
- Zustandまたは同等の軽量UIストア
- React Spring、GSAP、または独自の減衰スプリング
- Rapierは演出専用に使用可能。ルール状態を物理結果へ依存させない
- スコープされたCSS
- PWA対応

### バックエンド

- Firebase Authentication。未登録ユーザーは匿名認証し、同じブラウザではIDを維持
- Cloud Firestore: 部屋メタデータ、永続イベント、監査ログ、閲覧者別ビュー
- Firebase Realtime Database: presence、heartbeat、短寿命の接続状態に使用可能
- Cloud Functions for Firebase v2、またはCloud Run: 全ルール判定、シャッフル、タイマー、失格、順位、閲覧者別ビュー生成
- Firebase App Check
- Firebase Emulator Suite
- Firestore TTLまたは定期クリーンアップ

### 低遅延通信

- WebRTC DataChannelは、カーソル、エモート、注目視点、アニメーション開始通知、将来の音声などの非権威データだけに使う
- FirebaseをWebRTCシグナリングに使う
- カードの正体、手番、ルール結果、乱数、順位、タイマー失効をWebRTCメッセージだけで確定しない
- WebRTCが失敗してもFirebaseだけで完全にプレイできるフォールバックを持つ
- 最大6プレイヤーと観戦者数を考慮し、無制限mesh接続を避ける

### テスト

- Vitest
- fast-checkなどのプロパティテスト
- Firebase Emulator統合テスト
- Playwright複数ブラウザコンテキストE2E
- axe-core
- 主要画面のスクリーンショット比較
- ESLint、Prettier、TypeScript typecheck

## 権威状態と閲覧者別ビュー

単一のFirestore部屋ドキュメントを全員へ丸見えにしないでください。ブラインドモードでは、同じカードが「所有者には非公開、所有者以外には公開」になるため、閲覧者ごとの投影が必要です。

### 権威状態

- カードの全実体を含む状態はCloud Functions／Cloud Runだけが読める領域へ保存
- 一般クライアントからの直接read/writeをSecurity Rulesで拒否
- カード移動、シャッフル、効果、順位、タイマーをトランザクションまたは直列化されたコマンドで更新
- 乱数はサーバー側で生成
- クライアントのアニメーション完了をゲーム進行条件にしない

### プレイヤー専用ビュー

各プレイヤーにサーバーが次を投影してください。

- 自分の通常札: 表面を含む
- 自分のブラインド札: 不透明ID、裏面、位置、選択可否だけ。スートとランクを含めない
- 他人の通常札: 表面も推測可能IDも含めず、裏面表示トークンと枚数だけ
- 他人のブラインド札: 表面とブラインド印を含む
- 場、捨て札、公開効果、順位: 全公開

### 観戦者ビュー

- 全プレイヤーの全手札を表面付きで投影
- ブラインド札にはブラインド印を残し、所有者本人には見えていないと分かるようにする
- 観戦者のルール操作はサーバー側で拒否

本作では、外部観戦者が全手札を見られること自体が確定仕様です。一般的な公平性を理由に無断で隠さないでください。ただし役割とアクセスは監査してください。

- ルールブック

### 4. 配札

- ダイヤ3所有者を示して最初の手番へ誘導
- ブラインド札は所有者に裏面、他人に表面

## 3Dサロンのアートディレクション

### 空間

- 深い夜色、黒檀、ウォールナット、真鍮、濃緑または深紺のフェルト
- 高級ホテルのプライベートゲームルームを思わせる完全独自デザイン
- 平面背景だけでなく、簡易3D室内、パララックス、環境マップで奥行きを持たせる
- 暖色ペンダントライト、弱いリムライト、環境光
- ACES Filmic Tone Mapping、適切な露出、控えめなBloom、接触影
- フェルト、紙、木、金属の粗さを明確に分ける
- 暗すぎてカードを読めない状態にしない

### 円卓

- 高分割の円柱または円盤を基礎とし、X/Z半径を同一にする
- ワールド行列にも非等方スケールを残さない
- フェルト面、木製側面、真鍮縁、カード置き場、捨て札トレイを別マテリアルにする
- 面取りと正しい法線
- 3～6席を円周上へ等間隔配置
- 閲覧者本人または注目プレイヤーを画面手前へ回転
- 観戦カメラでもモデル自体を楕円変形しない

### カメラ

- 着席視点より少し高い位置から中央を見る
- 極端な広角を避け、35mm換算45～60mm相当を目標にする
- 観戦時は少し高く、注目プレイヤーと場を同時に読む
- 切替は酔いにくい1秒前後の減衰補間
- 縦長端末ではカメラ、扇角、カード縮尺、安全領域を同時に調整
- 手札の画面包絡矩形を測定し、最低90%がビューポート内かつUI非重複になるまで補正
- reduced motionでは即時切替または短いクロスフェード

### カード

- 厚みと丸角のある実3Dメッシュ
- 紙またはコットンカードの微細な粗さ、縁、印刷、わずかな反り
- 小画面でも数字とスートを即読できる表面
- 独自の幾何学模様と箔押し風の裏面
- 2枚のJokerを視覚識別可能にしつつ強さは同一
- カードフェイス、Joker、裏面は完全オリジナル
- 接触影、わずかな高さ差、自然なスタック回転
- InstancedMesh、アトラス、共有ジオメトリで最適化
- 選択時は持ち上げ、縁、音、触覚を同期
- Pointer Eventsへ統一し、touchstartとclickの二重発火を防ぐ

### アニメーション

- 配札: デックから弧を描いて各席へ着地
- 選択: 指でつまむように上昇
- 提出: 中央へ滑り、前の場札を少しずらして積む
- パス: 席ネームプレートへ短い表示
- 場流れ: トリック全体を捨て札トレイへ掃く
- Joker擬態: 反転し、宣言スート・ランクを金縁表示
- 失格: 手札を公開して捨て札へ移す
- 途中参加・再接続時は履歴を再生せず現在状態へ復元

Rapierなどの物理は見た目の揺れや落下だけに使い、カード所有や合法性を決めないでください。

## 対局画面

### 常設HUD

- 左上: ブランド、退出
- 上中央: 現在手番、残り秒数、接続状態
- 右上: 自分の3Dアバターポートレートと名前
- 卓上右側: 革命、Jバック、リバース、縛り
- 下中央: 「選んだ札を出す」「パス」
- 左下: ログ／チャット
- 待機中だけ: ルームID、コピー、退出、ホスト開始

英語だけのボタンにせず、日本語動詞を主表示にしてください。無効理由を視覚・フォーカス・スクリーンリーダーで確認可能にします。

### プレイヤー表示

- 各席に3Dアバター
- 名前、残り枚数、接続、順位、ホスト印
- 現在手番の席に柔らかなリングライト
- 進行方向を円卓外周矢印で表示
- 飛ばされる席、リバース、場流れを空間演出
- 普通の相手手札は裏面
- 相手のブラインド札だけ表面とブラインド印

### 自分の手札

- 画面下へ扇状配置
- 表向き通常札を強さ順、その後ろにブラインド札をランダム順
- 革命・Jバック時も勝手な並び替えを強制せず、任意ソートを提供
- ブラインド札へ中身を推測できる色、DOM属性、ファイル名を含めない
- 多枚数時は扇角、重なり、縮尺、カメラを協調調整
- 全カードへポインター・キーボードで到達可能
- 下部操作ボタンと重ねない

### 提出フロー

1. カードを選ぶ。
2. クライアントは候補合法性だけを案内する。
3. Joker混在なら各Jokerの擬態先を選ぶ。
4. ブラインドを含むなら「失敗すると即失格」の最終確認。
5. submitPlayを一度だけ送る。
6. サーバー承認後に提出アニメーションを確定。
7. 却下時はカードを戻し、具体的理由を表示。

## 特殊効果UIと3D演出

すべての強制効果は、画面を閉じても同じ保留効果へ戻れるようにし、部屋を永久停止させないでください。

### A奪い

- 合計枚数と対象別配分を指定
- カメラを対象席へ移動
- 通常札は裏向きで選ぶ
- 対象のブラインド札は表面とブラインド印を見せる
- カードが自分へ飛び、表向き通常札になる
- 複数対象でも最後に一回の原子的コマンドで確定

### 7渡し

- 残り手札を選び、相手アバターまたは名前へドラッグして割当
- タッチ・キーボード用に「カードを選択→相手を選択」の代替
- 確定前に誰へ何枚かを一覧表示
- 移動したカードは受取人の表向き通常札

### 10捨て

- 残り手札から必要枚数を選ぶ
- ブラインド札は裏面のまま選ばせ、確定後に公開
- 捨て札トレイへ滑らせる

### Qボンバー

- 3から2、Jokerまでのランク選択パネル
- 必要数の異なるランクを選ぶまで確定不可
- 全員の該当カードを短く浮かせ、同時に捨て札へ移動
- 同時に0枚になった人を同順位として同時表示

### K回収

- 公開捨て札をページングまたは3Dトレイで閲覧
- 必要枚数または存在する全枚数を選ぶ
- 現在の場・未終了トリックは含めない
- 階段ではほかの選択式効果より先に処理

### 状態効果

- 4リバース: 円卓外周矢印を反転
- 5スキップ: 飛ばされる席を順番に点灯し、2n-1を視覚化
- ろくろ首・救急車: 識別可能な短い場流れ演出
- 8切り: 同じ階段の全効果完了後だけ強いスイープ演出
- Jバック: 卓の状態色と強さ方向表示を反転
- 革命: 卓中央紋章、照明、強さインジケーターを切替

### カットイン

- 効果名、原因カード、実行者を短く表示
- 操作を長時間遮らない
- 連続階段効果をキュー処理
- 演出スキップで効果処理を失わない

## 観戦

### 入室

- ロビーのIDまたは公開一覧から観戦を選べる
- 待機、配札、対局、終了直後のいつでも参加可能
- 観戦者はプレイヤー枠と開始条件に数えない

### 観戦画面

- Play／Passを完全に隠す
- 「観戦中」と現在注目中の名前を常時表示
- プレイヤー切替ボタンを用意し、aria-pressedを付ける
- 酔いにくい短いカメラ補間で注目席を手前へ
- 注目プレイヤーの手札を自分の手札と同等の大きさで表示
- 何度でも切替可能
- 全プレイヤーの全手札を閲覧可能
- ブラインド札には「所有者本人には見えていない」印
- 上がったプレイヤーを自動的に同じ観戦UIへ移す
- 390px幅でも切替UI、手札、ログを重ねない

## 完全3D共通アバター

### 基本方針

アバターは大富豪専用の顔アイコンではなく、将来のスポーツ、ボードゲーム、パーティーゲームでも同じ人物を使えるゲーム横断キャラクターにしてください。

- デフォルメされた親しみやすい頭身
- 小さくても個体識別しやすいシルエット
- 年齢、性別、人種を固定しない
- フルボディ共通ヒューマノイドリグ
- 顔のblend shapeまたはボーン
- 髪、帽子、眼鏡、衣装、アクセサリー用標準ソケット
- 安定したavatar schemaとversion migration
- GLB、Draco/Meshopt、KTX2/Basis最適化
- 卓上3D、全身画面、軽量ポートレートで再利用

自由描画、画像アップロード、任意メッシュアップロードは作らないでください。

### エディター

- 3Dターンテーブルプレビュー
- ドラッグ回転、ピンチ／ホイールズーム、正面へ戻す
- 顔、髪、表情、服、装飾、体格タブ
- 各パーツの3Dサムネイル
- 色、素材、柄を別レイヤーで選択
- ランダム生成
- 元に戻す／やり直す
- プリセット保存、複製、削除
- 保存前後比較
- モバイルでは2段グリッドまたはドロップダウンへ変形
- フォーカストラップ、Escape、元フォーカス復帰、背景スクロール停止

- ベルベット、サテン、レザー、刺繍、金糸、銀糸、真鍮、宝石、エナメルのPBR素材

## 運用と監視

- Sentryまたは同等の導入境界

## 作業手順

### フェーズ1: 仕様と基盤

1. ルールブックを読み、ルールごとのテスト一覧を作る。
2. 既存アプリを読み取り専用監査し、ブランド資産と技術負債を分ける。
3. 新モジュール構成を作る。
4. 純粋ルールエンジンと単体テストを先に完成。

### フェーズ2: 権威バックエンド

1. Emulatorで認証、部屋、コマンド、個別ビューを構築。

## GitとPush

- 既存のユーザー変更を消さない
- 破壊的resetやcheckoutをしない
- 秘密情報をcommitしない
- フェーズごとに意味のある小さなcommit
- typecheck、unit、integration、E2E、build通過後にPush
- ユーザーは通常の作業commitとPushを事前承認しているため、毎回確認せず安全にPushしてよい
- force pushは禁止
- CIとdeploy結果を確認し、失敗したら修正を続ける
- Firebase本番resource新規作成、課金変更、Security Rulesの大幅な公開範囲変更だけは、実行前に影響を説明する
